# Decisions

One row per decision. Never rewrite an old row: a reversal is a new row that names the one it replaces.

The design rulings for the game itself live in the design docs (`docs/combat-design.md` and the proposals it names); this file starts with the move onto the shared working rules on 2026-11-10.

| ID | Decision | Reason | Chosen against |
| --- | --- | --- | --- |
| D1 | The project moves onto the owner's shared working rules (Tonttu84/ai-workflow) as a **solo** project: commits go to `main` and are pushed once the local gate is green. Commit messages follow Conventional Commits from here on, checked by the ai-workflow `commit-msg` and `pre-push` hooks in `.githooks/` (installed with `hooks/install.sh` in its default mode; a fresh clone turns them on with `make setup`) and by CI. `.githooks/*` keeps LF endings in `.gitattributes`, since Linux bash rejects CRLF scripts and this repo is checked out with `autocrlf`. The kind is the owner's choice (2026-11-10); the hook mode and the LF line are the agent's. | The owner moves every active project onto one way of working (ai-workflow D23). *The clone had no hooks of its own, so the default mode switches nothing off.* | *The `--git-hooks` mode (per clone only, nothing committed for CI to reuse); keeping the old prose commit subjects.* |
| D2 | `AGENTS.md` is the project map and `CLAUDE.md` is the single line `@AGENTS.md`. The old "Where we are" log (`CLAUDE.md` lines 81-586) moves unchanged to `docs/history.md`; `AGENTS.md`'s "Where we are" holds the current state only, rewritten in place when a slice finishes, with the slice's story in its commit message and, when worth keeping, a dated entry at the top of `docs/history.md`. `AGENTS.md` stays under 150 lines. The split is the owner's request (issue #2); the 150-line cap and where new history goes are the agent's choice. | The log was appended to after every slice and loaded into every session (issue #2): every session paid for history it rarely needed, and the current state was buried in it. | *Trimming the log in place (loses the reasoning behind rulings); a test enforcing the cap (a line count is easy to see in review).* |
| D3 | The local gate is `make gate`: the unit tests, both balance sims CI runs (`--n=200`, no-card and random bot), the UI smoke, the web export, then the function-limits report (D4). It mirrors the jobs of `.github/workflows/ci.yml`. Agent's choice. | The shared rules run the full gate locally before every push and let CI confirm. *The smoke is the only layout guard and the export the only build, so a unit-test-only gate would push the regressions they exist to catch.* | *`make test` alone; leaving the gate as a list of commands in a doc.* |
| D4 | Function limits, measured with Lizard (GDScript) over `src/` on 2026-11-10: cyclomatic complexity 15, length 60 lines, 5 parameters, the starting values of ai-workflow's `templates/function-limits.md`. Of 377 functions they flag 7 (1.9%), 10 (2.7%) and 9 (2.4%), 20 (5.3%) over at least one; the worst are `simulate.gd _init` (CCN 27, 115 lines), `roster_text.gd parse` (26, 98) and `character_token.gd _build` (26, 106). `make limits` (`scripts/function_limits.sh`) reports them as warnings and never fails; it runs at the end of `make gate`. Tests are not measured (`tests/ui_smoke.gd _run` alone is 568 lines, one scripted session). No code is refactored for this. Agent's choice. | *The starting values already flag only the worst few percent. The template has no GDScript linter config and the project uses no GDScript linter; Lizard reads GDScript and needs only Python.* | *Adding gdtoolkit's `gdlint` (a new toolchain for part of these measures); tighter limits (CCN 12 and 40 lines flag 2.4% and 6.1%).* |
| D5 | Dependabot version updates cover `github-actions` only (the template's schedule, the 1st and 15th, `ci` prefix); security updates are on. The Docker base image (`ubuntu:24.04`) and the Godot 4.5 download in `Dockerfile` and `ci.yml` stay pinned by hand. Agent's choice. | *The game has no package manager; its only dependencies are Godot, which Dependabot cannot track, and the CI actions. A Docker ecosystem would propose a new Ubuntu release, whose package names (such as `libasound2t64`) the Dockerfile depends on.* | *Adding the `docker` ecosystem.* |
